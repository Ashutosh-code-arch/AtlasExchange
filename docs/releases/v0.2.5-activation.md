## Activation evidence

- The v0.2.5 publication workflow passed repository verification, production builds, architecture
  scans, dependency audit, multi-architecture image scanning, publication, and provenance signing.
- Render runs the immutable v0.2.5 image digest. The public status contract reports application
  version `0.2.5`, and the readiness contract reports `ready` through the Worker.
- Direct requests to the Render API origin remain rejected with HTTP `403`; the application remains
  available through the Worker boundary.
- The API public-account flags were enabled before the matching browser flags. Registration and
  password recovery remained hidden at the Worker while the server-side negative control ran.
- A fabricated human-verification token was rejected with HTTP `400` and
  `HUMAN_VERIFICATION_FAILED`. A read-only PostgreSQL aggregate before and after the request remained
  exactly three identities: two active and one pending verification.
- The configured Turnstile secret rejected a fabricated token directly with
  `invalid-input-response`; it is not an always-pass test key.
- The final Worker version receives 100 percent of production traffic. Its public runtime document
  reports registration, password recovery, and human verification enabled, with only the Turnstile
  site key exposed to the browser.
- A controlled password-recovery request passed a fresh hosted Turnstile challenge and returned the
  generic accepted response only after the configured delivery adapter completed. The database
  recorded one new reset capability without changing the identity count. That capability was then
  consumed by a completed reset 54 seconds after issuance, and the corresponding
  `identity.password_reset.completed` security event was present. No credential, raw token, token
  digest, or recipient address was read or recorded in this document.
- The controlled signup, email verification, session, wallet, deposit, cross-user trade, and atomic
  settlement evidence recorded during the v0.2.4 attempt remains valid because v0.2.5 changes only
  Turnstile composition wiring and its regression coverage.

## Capacity and retained data

- The final aggregate remains three ordinary-user identities: two active and one pending
  verification. Seventeen places remain beneath the fixed 20-identity ceiling.
- The pending identity is the placeholder created by the failed v0.2.4 fabricated-token check. It
  was retained because activation did not authorize destructive account deletion.

## Deliberately excluded

- The 20th/21st-account and concurrent final-place boundary was not exercised against the live
  database; the isolated PostgreSQL integration suite covers that invariant.
- No real asset, custody operation, payment, withdrawal, or external order execution occurred.
- No account was deleted or granted an administrative role.
- Verification-resend delivery was not forced by creating another pending live identity. Its action
  binding and delivery behavior remain covered by the release test suite; registration and recovery
  independently proved the hosted Turnstile and SMTP boundaries.

## Activation result

The v0.2.5 negative control closed the v0.2.4 fail-closed incident: public identity flows now enforce
the configured Turnstile verifier at the composed production router. Registration and password
recovery are active for the capped beta. Existing-user access and simulated trading remain active.
