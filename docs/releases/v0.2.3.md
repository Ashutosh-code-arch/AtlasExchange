# Atlas Exchange v0.2.3 — Protected Operator Email Test

## Highlights

- Optional Profile action to test the deployed API's SMTP delivery path without a Render shell.
- Authentication, exact configured operator identity, Origin/CSRF validation, and server-loaded
  account email. No arbitrary recipient, content, link, or attachment input.
- Three attempts per 15 minutes per process, including failures, and a concurrent-send guard.
- Generic errors and an explicit distinction between SMTP acceptance and confirmed inbox delivery.
- Disabled by default. Demo-only activation requires authenticated TLS SMTP configuration and both
  public account flows to remain disabled.

## Deployment notes

- Publication scope: **API only**. Web and metrics-collector container images are not requested.
  The frontend is deployed separately as static assets with the existing Cloudflare Worker.
- No database migration: expected schema version remains 15.
- Publishing does not update Render/Cloudflare, send an email, or enable signup/recovery.
- Promote only the verified immutable API digest. Deploy updated frontend assets to the existing
  `atlas-exchange` Worker, not the example `atlas-exchange-demo` name.
- Keep `PUBLIC_REGISTRATION_ENABLED=false` and `PUBLIC_PASSWORD_RECOVERY_ENABLED=false` on both
  API and Worker. Keep `OPERATOR_EMAIL_TEST_ENABLED=false` until deliberate operator activation.
- Follow the [operator email test runbook](../engineering/operator-email-test.md), then disable the
  diagnostic again after confirming receipt. The limiter resets on process restart; it is not a
  public signup abuse-control mechanism.
- The previously recorded collector finding is not fixed or waived by this release. A passing
  API-only gate is not evidence that the entire container set is clear.

Atlas remains a simulation: no real custody, deposits, withdrawals, or external order execution.
