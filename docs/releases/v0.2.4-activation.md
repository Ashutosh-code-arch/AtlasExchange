## Activation evidence

- The API image publication workflow passed source verification, production builds, architecture
  scans, publication, and provenance signing. The published multi-architecture image digest was
  resolved before deployment.
- The Turnstile Managed widget is restricted to the exact production Worker hostname. The public
  runtime document contains only the site key, and the API-only secret is absent from browser
  configuration and source.
- The Worker CSP permits the Turnstile script and frame origin without widening other directives.
- The API was enabled before the matching Worker flags. Readiness passed before the browser controls
  were exposed. The Worker activation version receives 100 percent of production traffic.
- The activation runtime document initially reported registration, password recovery, and human
  verification enabled.
- Direct requests to the Render API origin remain rejected with HTTP `403`; the profile route remains
  available through the Worker.
- The pre-activation database contained one active ordinary-user identity. A controlled signup
  passed the hosted Turnstile challenge, produced the generic accepted response, delivered a real
  verification email, and became active through its one-time link.
- Post-verification aggregate state was two active identities. Both identities have only the `user`
  role, leaving 18 places beneath the fixed 20-identity ceiling.
- The controlled identity signed in through the production session boundary and opened USD and ETH
  wallets. A canonical simulated deposit of `10000 USD` succeeded.
- A controlled `BUY 1 ETH @ 2455 USD` was matched by a sell from the pre-existing, distinct identity.
  One fill settled atomically. The buyer's final balances were exactly `1 ETH` and `7545 USD`, with
  zero reserved balance; the persisted buyer and seller owners were distinct.
- Password recovery passed a fresh hosted Turnstile challenge. Atlas returned the generic accepted
  response only after the configured email-delivery adapter completed, and a fresh unconsumed reset
  capability was confirmed by aggregate read-only query. No credential or reset token was read or
  recorded.

## Deliberately excluded

- The 20th/21st-account and concurrent final-place boundary was not exercised against the live
  database; the isolated PostgreSQL integration suite covers that invariant.
- No real asset, custody operation, payment, withdrawal, or external order execution occurred.
- No account was deleted or granted an administrative role.
- Verification-resend delivery was not forced by creating another pending live identity. Its action
  binding and delivery behavior remain covered by the release test suite; registration and recovery
  independently proved the hosted Turnstile and SMTP boundaries.

## Failed activation gate and response

The final negative control submitted a fabricated human-verification token. The registration endpoint
incorrectly returned the generic accepted response because the identity module factory constructed the
Cloudflare adapter but did not forward it to the HTTP router. The request may have created one pending
placeholder identity; no automatic deletion was performed.

Public registration and password recovery were immediately disabled on both the API and Worker. The
deployed v0.2.4 API otherwise remains available to existing users. Activation is blocked until a patch
release adds the missing composition wiring, verifies the seam against real PostgreSQL, and passes the
live negative control before either public flow is reopened.
